01The problem问题描述

AI agents still struggle with OS-kernel engineeringAI Agent 解决 OS 内核智能体工程仍很困难

Requirement development, bottleneck analysis, bug finding, bug fixing — every kernel agent-engineering task rests on one core problem:需求开发、瓶颈分析、bugfinding、bugfix——每一项内核智能体工程任务都建立在同一个核心问题之上：

Correct & efficient understanding of the code.对代码的正确、高效理解。
Requirement dev需求开发 Bottleneck analysis瓶颈分析 bugfinding bugfix Code review代码审查 Backporting补丁回移
Today's retrieval: coarse-grained & low-efficiency今天的检索方式：粗粒度、低效率

Agents fall back to grep / glob / read — pure-text retrieval that is coarse-grained and low-efficiency:Agent 只能退回 grep / glob / read——粗粒度、低效率的纯文本检索：

✕
Imprecise walkthrough走读不精准 — text matches scatter across dead #ifdef branches and same-named statics.——文本匹配散落到死 #ifdef 分支与同名 static 里。
✕
Inefficient walkthrough走读不高效 — many round-trips, 10k+ tokens, to piece together what one graph query answers.——多次往返、10k+ token，才能拼出一次图谱查询就能答的事。
Existing work — built on Tree-sitter AST现有工作 —— 建立在 Tree-sitter AST 之上
CodeGraph, Codebase-Memory, Semcode — all built on Tree-sitter (static AST). None treats the compiler semantic IR as the foundation for a kernel code graph, so none meets these requirements: CodeGraph、Codebase-Memory、Semcode——均建立在 Tree-sitter（静态语法树 AST）之上，未把编译器语义 IR 作为内核代码图谱的构建基础，因此均无法满足：
①Conditional compilation条件编译

Multi-ISA, multi-config, multi-platform, multi-version — #ifdef CONFIG_*, #ifdef __x86_64__…多 ISA 架构、多配置、多平台、多版本 —— #ifdef CONFIG_*、#ifdef __x86_64__…

✕Tree-sitter AST: parses every branch blindly — cannot prune by config.Tree-sitter AST：盲目解析所有分支——无法按配置裁剪。
✓Compiler IR (KGraph): indexes only what defconfig compiles — dead branches never enter the graph.编译器 IR（KGraph）：只索引 defconfig 真正编译的代码——死分支永不进图。
②Function-pointer indirect references函数指针间接引用

Architectural extensibility via ops tables — device drivers, VFS, net/proto ops. Call sites like f_op->read_iter().经 ops 表实现的架构可扩展性——设备驱动、VFS、net/proto ops。调用点如 f_op->read_iter()。

✕Tree-sitter AST: the call site has no impl name — the target is unresolvable.Tree-sitter AST：调用点无实现名——目标无法解析。
✓Compiler IR (KGraph): ops_bind edges connect every ops-table field to its concrete implementation.编译器 IR（KGraph）：ops_bind 边把每个 ops 表字段连到具体实现。
③Complex macro expansion复杂宏展开

EXPORT_SYMBOL, SYSCALL_DEFINE*, module_init, DEFINE_* — define the real symbols and entry points.EXPORT_SYMBOL、SYSCALL_DEFINE*、module_init、DEFINE_*——定义真实符号与入口。

✕Tree-sitter AST: macro bodies are opaque text tokens — symbols can't be identified.Tree-sitter AST：宏体是不透明文本 token——符号无法识别。
✓Compiler IR (KGraph): indexes macro-expanded real symbols, with names and positions.编译器 IR（KGraph）：索引宏展开后的真实符号，带名字与位置。
02Product positioning产品定位

A compiler-built knowledge graph for AI agents on kernel-class code面向内核类源码、为 AI Agent 而生的编译器级代码知识图谱

KGraph is a code knowledge-graph engine built with compiler technology (semantic-analysis IR), designed for AI agents working over general kernel-class source with strong build dependencies.KGraph 是一种利用编译器技术（语义分析 IR）构建的、面向通用内核类源码（强构建依赖）、为 AI Agent 设计的代码知识图谱引擎。

In essence本质上

The KGraph code graph always reflects a "committed + compiled" stable snapshot — a high-density, attributed directed graph expressing code semantics and structure: functions / variables as nodes, references / macro-expansions / function-calls as edges.KGraph 代码图谱永远反映的是一个"已提交 + 已编译"的稳定快照——一个带属性的高密度有向图，表达代码语义与结构：函数 / 变量为点，引用、宏展开、函数调用等为边。

04Key technology关键技术

Built on compiler truth建立在编译器真相之上

Every capability flows from indexing what the compiler actually emits — post-preprocessor, config-resolved, symbol-disambiguated.每一项能力都源自"索引编译器真正产出的东西"——预处理后、配置已解析、符号已消歧。

🎯

Compiler-aware编译器感知

Indexes post-preprocessor truth. A file changed but not built is a draft, not truth.索引预处理后的真相。改了但没编译的文件只是草稿。

🧩

Config-aware配置感知

Only code your defconfig compiles. Dead #ifdef branches are excluded entirely.只保留你的 defconfig 编译的代码。死 #ifdef 分支被整体排除。

🔀

Macro-resolved宏已展开

EXPORT_SYMBOL, SYSCALL_DEFINE*, module_init — expanded to real symbols with accurate positions.EXPORT_SYMBOL、SYSCALL_DEFINE*、module_init——展开为真实符号，带准确位置。

🔗

Function-pointer-callable函数指针可达

ops_bind edges resolve indirect calls through ops tables — the grep blind-spot.ops_bind 边解析经 ops 表的间接调用——grep 的盲区。

🗄️

SQLite-nativeSQLite 原生

Single-file graph DB: WAL concurrency, recursive-CTE traversal, FTS5 symbol search.单文件图数据库：WAL 并发、递归 CTE 遍历、FTS5 符号搜索。

🔢

Per-TU disambiguation逐 TU 消歧

Same-named static helpers in different translation units stay distinct, via clang symbol resolution.不同翻译单元里同名的 static 辅助函数保持独立，靠 clang 符号解析。

08Quickstart快速开始

Three commands to a queryable kernel三步命令，得到可查询的内核

Once your kernel has a compile_commands.json, setup is three commands. Bundles Python 3.10 + scip-clang — Linux x86-64 only.内核有了 compile_commands.json 后，三步即可。内置 Python 3.10 + scip-clang——仅 Linux x86-64。

npm install -g @ajksunkang-aios/kgraph
Installs the shim + platform bundle (Python 3.10 + scip-clang).安装 shim + 平台 bundle（Python 3.10 + scip-clang）。
kgraph install
Auto-wires the MCP server into your agents (Claude, Cursor, Codex…).自动把 MCP server 接入你的 agent（Claude、Cursor、Codex…）。
cd /path/to/linux && kgraph init .
Builds the graph. Needs compile_commands.json (run make CC=clang LLVM=1 + scripts/clang-tools/gen_compile_commands.py first).构建图。需要 compile_commands.json（先 make CC=clang LLVM=1 + scripts/clang-tools/gen_compile_commands.py）。

Then restart your agent and ask structural questions — it calls KGraph instead of grepping:然后重启 agent，问它结构化问题——它会调 KGraph 而非 grep：

ask your agent问你的 agent

> What implements什么实现了 ->read_iter across the kernel?（全内核）？
